## 1. 产品形态

EcomAgent 是面向**单个电商商家**的私有化经营决策与执行系统。它服务选品、商品、利润、推广、运营和客服的日常闭环，但不把这些能力拆成彼此独立、自由协作的多个 Agent；系统以统一业务事实、规则、审批和审计为基础，在具体工作台中调用受控 AI。

每个商家独立部署一套 Docker 环境和数据库；系统可先服务自营业务，再复制交付给其他商家，但不提供多商家共享实例或 SaaS 服务。首批业务为居家收纳用品，使用淘宝/通用货架电商的内容表达方式。P0 仅使用虚构品牌“栖纳家居”的 Demo 数据、文案与图片。

## 2. 五个经营工作台与公共底座

| 工作台 | 核心问题 | AI 可以做什么 | 人必须决定什么 | 阶段 |
| --- | --- | --- | --- | --- |
| 选品中心 | 什么商品值得做 | 基于可追溯数据生成机会评分、理由和风险 | 是否立项、供应链和类目判断 | P1 起 |
| 商品中心 | 如何形成可卖的商品资产 | 生成标题、卖点、详情、FAQ、图片候选 | 校验商品事实、审批和导出 | P0 |
| 利润中心 | 卖出后是否赚钱、可否降价 | 计算预估毛利、提出价格风险提示 | 成本口径、价格底线和调价审批 | P0 基础，P1 扩展 |
| 推广中心 | 用什么素材推广、效果如何 | 生成图文素材包、归纳效果变化 | 预算、投放动作和素材采用 | P0 素材基础，P1 扩展 |
| 运营中心 | 店铺有哪些异常和待办 | 汇总指标、预警、提出处理建议 | 经营策略、调价和执行确认 | P1 起 |
| 客服中心 | 顾客问题如何安全处理 | 事实问答、风险分级、草稿和转人工 | 中高风险回复、售后裁决 | P0 售前，P2 后扩展 |

所有工作台共用以下公共底座：

- **经营事实**：商品、SKU、成本、价格、库存、内容、素材、订单和售后等统一标准对象。
- **指标与来源**：每个选品、毛利、推广和运营指标都记录数据来源、时间、口径与新鲜度。
- **规则与审批**：价格底线、最低毛利、素材审批、自动回复白名单和未来写操作白名单统一管理。
- **任务与审计**：AI 生成、人工确认、导出、同步、失败和未来执行动作均可追溯。

## 3. 角色与权限

P0 实现本地账号登录和固定角色权限，不实现多租户、组织架构、成员邀请、SSO 或细粒度自定义权限。

| 角色 | 可访问工作台 | 主要权限 |
| --- | --- | --- |
| 管理员 | 全部 | 拥有其他角色全部权限；管理账号、模型、成本口径、经营规则、审批、审计和未来平台授权 |
| 运营/内容 | 商品、素材、利润基础 | 维护商品与成本事实，生成内容/图片，查看毛利，提交审批 |
| 客服 | 顾客会话、待审核回复、转人工队列 | 使用已授权事实，审核中风险回复，记录转人工原因 |
| 顾客 | 独立售前咨询页 | 提问并接收自动回复、人工回复或转人工提示 |

财务、推广和运营是工作台能力，不在 P0 新增独立后台角色；中小商家可由管理员或运营角色承担，后续确有分工需求时再设计权限扩展。

## 4. 顾客售前服务流程

```text
顾客在独立咨询页提问
-> 识别意图并评估风险
-> 查询商品/SKU/已审核 FAQ/规则事实
-> 低风险且事实完整：自动回复
-> 中风险：生成草稿，客服审核后发送
-> 高风险、事实缺失、工具失败、投诉或明确要求人工：转人工
-> 保存来源摘要、风险等级、处理方式、操作人与会话日志
```

自动回复仅限已审核且无歧义的材质、尺寸、容量、颜色、包装清单、安装/使用方式和适用场景。价格、库存、优惠、具体发货/到货承诺、退款/补发/换货、质量争议、认证或功效宣称，以及任何未录入信息，均不得自动回复。

## 5. AI 能力边界

| 场景 | AI 的职责 | 人的职责 |
| --- | --- | --- |
| 选品与经营分析 | 在已授权数据上计算评分、归纳机会与风险 | 确认数据口径和经营决策 |
| 商品与推广素材 | 根据已录入事实生成图文候选和结构化素材包 | 校验事实、版权、主体保真和采用范围 |
| 毛利与价格 | 计算毛利、提示价格底线和生成调价建议 | 维护成本、设定底线、审批任何调价 |
| 顾客问答 | 分类、检索、低风险自动答复、生成草稿、识别转人工 | 审核中风险回复，处理高风险和投诉 |
| 平台写操作 | P0-P2 不执行；后续仅按批准规则生成执行请求 | 对发布、推广、改价、退款等动作负责 |

系统不得承诺“链接排名第一”。平台排名由价格、销量、转化、评价、服务、广告和平台算法等共同影响。任何未来自动调价必须以最低毛利、调价幅度、频率、库存和人工停用开关共同约束。

## 6. 业务核心与渠道接入中心

系统在逻辑上拆分为两个系统：平台无关的 **EcomAgent 业务核心**，以及专门承担外部平台差异的 **渠道接入中心（Integration Hub）**。两者同属一个代码仓库，但使用独立服务模块、数据库权限和运行队列；通过内部 API 与异步事件通信，不共享数据库。

```text
业务核心
  选品 / 商品 / 利润 / 推广 / 运营 / 客服 / 规则审批 / 审计
        -> 标准数据模型、建议或已审批执行请求 ->
渠道接入中心
  授权 / Token / 字段映射 / 只读同步 / 平台执行 / 限流 / 重试 / 告警
        -> 淘宝 Connector | 拼多多 Connector | 抖音/抖店 Connector | 小红书 Connector | ERP Connector
```

业务核心负责判断“是否应调价、应使用何种素材、是否允许执行”；渠道接入中心只负责转换并执行已批准的具体平台动作。业务核心不保存平台 Token、回调原文、限流状态，也不硬编码平台字段。任一 Connector 故障只暂停自身任务，不阻断业务核心或其他渠道。

阶段边界如下：

- **P0**：不接平台，完成商品、成本毛利、素材、售前客服、审批和审计基础。
- **P1**：使用 CSV/Excel 或授权导出数据，完成选品评分、利润分析、推广复盘、运营看板和调价建议。
- **P2**：取得合法授权后，渠道接入中心逐 Connector 只读同步商品、订单、物流、售后和经营事实。
- **P3**：按单渠道、单动作开放已审批的发布、素材推送或受控调价；不承诺排名，不默认全自动。

## 7. P0 技术基线

- 本地 Docker 部署：Vue + FastAPI + PostgreSQL。
- P0 开发期统一使用阿里云百炼 DashScope：Qwen 文本模型与 DashScope 图像模型均通过 Provider 适配层调用。
- 生产/试用阶段由每个商家配置并保管自己的 DashScope API Key；系统只读取环境变量，不记录或展示密钥。
- P0 顾客咨询页为本地演示入口。面向外部顾客的正式访问，需要在后续部署到具备公网 HTTPS 域名的服务器。
