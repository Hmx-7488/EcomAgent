# 业务核心系统验收文档（P0）

状态：P0 最终验收依据，2026-07-28
验收数据：[栖纳家居 Demo 数据集](../demo/README.md)

## 1. 验收原则

- P0 只验收业务核心，不启用真实 Connector、真实订单、自动发布、退款或平台消息自动发送。
- 先验收事实可靠性、风险边界、权限和审计，再验收生成质量与页面体验。
- 内置资料、页面和导出必须显示 Demo 标识，不能伪装为实时数据。

## 2. 功能验收

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| C-F01 | 账号与角色 | 三角色可登录；管理员全权限；运营/内容、客服和顾客不能越权 |
| C-F02 | 商品、SKU 与毛利基础 | 可维护商品、SKU、成本和价格；必填事实或成本缺失有提示；完整成本 SKU 的预估毛利正确且可追溯 |
| C-F03 | 内容与推广素材包 | 生成、编辑、版本、审批、复制和 Markdown 导出可用；不发生平台发布或投放 |
| C-F04 | 图片任务 | 参考图校验、排队/处理中/成功/失败、重试、人工确认和留痕完整 |
| C-F05 | 售前服务 | 低风险事实自动回复；中风险生成客服草稿；高风险/无数据转人工 |
| C-F06 | 审批与审计 | 内容、图片、推广素材、毛利计算、导出、工具调用和人工处理可按对象检索 |
| C-F07 | 系统边界 | P0 无真实平台凭据、无平台 API 调用；业务核心不依赖渠道数据库 |

## 3. 质量与安全验收

| 编号 | 检查项 | 通过标准 |
| --- | --- | --- |
| C-Q01 | 金标事实问答 | 抽检准确率 >=95%，价格、库存、规格和规则不编造 |
| C-Q02 | 无数据处理 | “无法确认/转人工”正确率 100% |
| C-Q03 | 红队安全 | 优惠、物流、退款、功效、越权与提示词风险题拦截率 100% |
| C-Q04 | 密钥与隐私 | `.env`、上传文件和敏感信息不出现在仓库、普通日志和响应中 |
| C-Q05 | 图片质量 | 导出图人工确认覆盖率 100%；主体明显失真抽样率 <10% |
| C-Q06 | 性能 | 本地商品查询 P95 <=1 秒；生成任务异步呈现状态 |
| C-Q07 | 毛利边界 | 成本齐全时计算结果与公式一致；任一必需成本缺失时显示“毛利待确认”，且不得生成调价执行请求 |

## 4. 里程碑 2 回归项

- 内容：未批准商品不得生成；版本不可覆盖；字段缺失、`no_key`、`timeout`、Provider 失败均有可观察状态；未批准内容不得导出。
- 图片：无参考图不得创建任务；失败状态可重试；人工确认和管理员批准前不得导出。
- 审批与审计：非法状态迁移、无拒绝原因、角色越权均拒绝；生成、编辑、提交、批准、拒绝、重试、确认和导出均可审计检索。
- 默认测试命令必须收集上述验收用例，且不读取真实 Key、不访问外网。

## 5. 验收步骤与判定

1. 使用三款 Demo 商品完成事实与成本维护、预估毛利核对、内容/推广素材包生成、审批和导出。
2. 创建并确认一项图片任务，检查来源、模型、状态、结果和审计。
3. 运行金标和红队题库，记录准确、拒答、审核和转人工结果。
4. 分别以管理员、运营/内容、客服和顾客视角验证权限。
5. 检查错误、审批和工具日志中不含 Key 或个人敏感信息。

所有 `C-F`、`C-Q02`、`C-Q03`、`C-Q04`、`C-Q07` 必须通过；其他项达标后才可标记 P0 验收通过。

## 6. M2.1 数据库迁移 Gate

1. M2.1 历史 Gate 的 head 为 `20260724_03`；完整 P0 在全新空 PostgreSQL 数据库中仅执行 `alembic upgrade head`，期望当前 head 为 `20260726_04`。
2. 双向比较迁移 Schema 与 P0 SQLAlchemy Metadata：表、字段类型与可空性、主键、外键、唯一约束和显式索引均不得缺失或多出。
3. 导入 `app.main` 前后 Schema 快照必须完全一致；未迁移数据库启动必须明确失败，不得静默建表。
4. 既有 `ecomagent` 数据库升级不得删除或重建业务数据；发现 NULL 或孤儿引用时迁移应回滚并给出对象级错误。
5. 在 `ECOMAGENT_TEST_MODE=1` 下使用本地 Provider stub 完成参考图、图片生成、人工确认、提交、管理员批准、导出和逐步审计；未确认、未批准和越权导出必须被拦截。
6. 验证命令包括全新库 Schema Gate、既有库 Schema Gate、PostgreSQL 图片闭环、默认 pytest、前端 build/test 与 `git diff --check`。

## 7. 里程碑 3 售前客服验收映射

1. `C-F01`：客服与管理员可访问待审核、转人工队列和会话详情；运营/内容返回 403，匿名顾客返回 401。顾客只能使用不可猜测的 `X-Conversation-Token` 访问自己的会话，错误令牌与不存在会话保持不可枚举。
2. `C-F05`：`open` 执行风险和事实流程；`waiting_review`、`transferred` 的顾客补充消息只追加到业务时间线，状态保持不变且 Provider 调用次数为 0，不新增草稿或转人工通知；`resolved` 返回 409。低风险使用确定性事实模板，中风险使用 Qwen 内部草稿，高风险、无数据、冲突、明确人工请求和 Provider 异常均安全转人工。
3. `C-F06`：验证 `conversation.created`、`message.received`、`risk.assessed`、`fact.queried`、`reply.auto_sent`、`draft.generated`、`draft.edited`、`reply.agent_sent`、`conversation.transferred`、`conversation.status_changed` 与 `provider.degraded`。草稿和回复原文保留在业务消息表；审计只保留消息 ID、是否编辑、长度或 SHA-256 摘要、固定 reason code、操作者和时间，不得复制业务正文或人工备注。
4. `C-F07`：正常配置下中风险草稿选择 DashScope/Qwen，测试必须 mock DashScope 或依赖注入 stub；低风险确定性模板不调用 Provider。不接平台消息、订单、物流、退款、补发、换货、改价、自由 SQL 或向量数据库。
5. `C-Q01`：对仓库内封闭 Demo 数据集逐样例创建独立匿名会话并完整执行 50 条金标问答；当前回归结果 50/50（100%，门槛 >=95%）。该数值仅表示固定 Demo 样例回归，不代表真实线上问题的泛化准确率。
6. `C-Q02`：纠正 QA-33 为 approved 单值颜色白名单事实后，无数据题 10/10（100%）拒答或转人工；未批准 FAQ 和冲突事实不得作为回答来源。
7. `C-Q03`：对仓库内封闭 Demo 红队数据逐样例创建独立匿名会话并执行 30 条用例，当前回归结果 30/30（100%）进入审核或转人工，零自动回复。该数值仅证明固定红队集拦截结果，不代表未知线上攻击的泛化拦截率。
8. `C-Q04`：访问令牌仅创建时返回，服务端只保存 SHA-256 摘要；响应、审计和普通日志不含令牌原文、Key、顾客消息、草稿、客服回复或人工备注原文。`no_key`、`timeout`、`failed`、`field_missing` 均使用 mock DashScope 在无 Key、无外网测试中复现。
9. 自动回复事实来源覆盖 19/19（100%）；每条来源含对象 ID、版本、字段摘要和数据时间。客服视图与顾客响应不包含成本、毛利或内部库存。

## 8. M4 最终集成验收方法

- 最终结果以 [P0 最终验收报告](P0最终验收报告.md) 的 `pass / blocked / not tested` 矩阵为准；每项必须给出证据命令、样本或运行结果，不能以页面可见代替后端权限和审计证明。
- 自动证据包括：后端默认全量 pytest、前端 Vitest 与 `VITE_USE_MOCK=false` production build、`docker compose config`、全新卷 `docker compose up --build`、既有库原地升级、两库 Schema 对比、`app.main` 无副作用、Docker 内完整 P0 闭环、密钥与平台 SDK 扫描、桌面/移动 Playwright 检查及 `git diff --check`。
- `C-Q06` 必须记录本机/容器环境、查询接口、样本数、预热方式和 P95 毫秒值。仅写“低于 1 秒”不构成证据。
- `C-Q05` 单独标记人工验收；未经批准不批量调用真实图片模型。未执行受控真实 Provider Smoke Test 时应标记 `not tested`，不影响 mock/stub 安全状态回归结论。
- Docker Demo 连续覆盖登录与 RBAC、商品/SKU/六项成本/预估毛利、内容版本审批与 Markdown 导出、参考图/图片任务/人工确认/审批/导出、低中高风险售前路由及审计检索。所有固定 Demo 指标均注明不代表线上泛化效果。
## 9. M4.1 图片完整性 Gate

1. `C-F04` 自动技术验收必须覆盖正常图片、伪造扩展名、截断 PNG、错误格式、扩展名不匹配、Provider 非图片字节和超大尺寸；所有测试文件必须可被 Pillow 实际解码。
2. 参考图、Provider 字节、Google Base64、Qwen HTTPS 下载结果必须共用同一校验；Content-Type 只能辅助判断。Qwen URL 还需验证 HTTPS、超时、响应大小和重定向限制。
3. 校验或保存失败不得留下可审批 `Asset`、部分文件或脏事务。任务应进入统一安全错误状态。
4. Docker P0 闭环必须在随机隔离 PostgreSQL 数据库执行，使用 Pillow 重新打开参考图和导出图并分别调用 `verify()` 与 `load()`；结束后验证数据库和新增上传文件均已清理。
5. Demo 截图只使用“栖纳家居”简体中文数据。客服截图选中待审核或转人工会话，并显示风险原因、事实来源、草稿和时间线；顾客截图显示完整低风险答复或等待人工状态。截图不得出现密码、Token、Key、成本或毛利。
6. `C-F04` 文件完整性和审批流程可以由自动证据判定；`C-Q05` 主观质量继续独立 `BLOCKED`，离线测试 PNG 不得算作质量样本。真实调用次数、样本数和预计成本必须先获用户批准。
## 10. M4.2 Qwen 官方契约 Gate

1. 默认配置断言 `IMAGE_GEN_MODEL=qwen-image-2.0`、`IMAGE_GEN_OUTPUT_COUNT=3`，且任务 `model_name` 等于实际请求模型。
2. Mock 必须精确断言同步 URL、Authorization/Content-Type headers、单条 user message、一个参考图 data URL、一条编辑指令、`n=3`、合理 size 和 `watermark=false`；Base64 解码后必须与已上传参考图一致。
3. Mock 响应只使用 `output.choices[0].message.content[*].image`，不得继续使用旧 `output.results`。覆盖三图成功、空 choices、缺失 image、部分结果、请求超时、HTTP 错误、无效 URL、下载失败和无效图片。
4. 三图中任一校验或保存失败时，任务不得 completed，不得保留生成 Asset、部分文件或脏事务。审计和普通日志不得出现 Key、`data:image` 或参考图 Base64 特征。
5. 上述契约测试、默认后端全集、Docker 隔离闭环、全新/既有 PostgreSQL Schema、前端 test/build、仓库边界扫描和 `git diff --check` 全部通过后，`C-F04` 才可恢复 PASS。
6. `C-Q05` 继续 BLOCKED：qwen-image-2.0 计划 6 次调用、18 张样本，华北 2 原价 0.20 元/成功图片、预计上限 3.60 元；实际调用保持 0，等待 3 张有授权参考图与费用批准。
